Phase 18 adds registry-controlled business configuration to the existing Laravel / PostgreSQL / Inertia / Vue application. Fortify, Spatie permissions and Phases 1–17 remain authoritative. No package, accounting ledger, provider integration or secrets store is added. Phase 19 is outside this change.

## Registry, schema and typed access

`SettingsRegistry` defines nine controlled groups: general, commerce, authors, payouts, refunds, products, support, notifications and reporting. Each entry defines its type, default/config compatibility source, server validation, help text, editability, sensitivity, snapshot requirement and reload requirement. Every entry is non-secret and editable; none needs a process restart. Types are string, email, integer, boolean, decimal, list and timezone. Decimal values are canonical two-place strings through existing `Money`/Brick arithmetic; currencies are never converted or combined.

`marketplace_settings` stores group/key, JSONB value, server-selected value_type, positive optimistic version, nullable restrictive updater FK and timezone-aware timestamps. Group/key is unique. `marketplace_setting_events` stores group/key, restrictive actor FK, historical actor display name, canonical old/new JSONB values and occurrence time. Its group/key/id index supports bounded audit queries. Audit rows have no editable controller/model operation. PostgreSQL triggers reject UPDATE/DELETE, and the setting-version trigger rejects identity changes or an update without exactly one version increment. Known groups/types and Order refund-window bounds are checked in PostgreSQL. Application registry semantics are deliberately enforced by application validation; PostgreSQL does not pretend to understand every PHP validator or reject every otherwise valid unknown key written by a privileged direct SQL operator.

`MarketplaceSettings` is the domain accessor. There are no scattered raw setting queries or static process-lifetime values. Ordinary precedence is DB override → existing config/environment value → registry default. Nullable contact input is canonicalized to an empty display value. Before setting rows/table exist, safe defaults/config compatibility still work. Admin projections can show an unavailable policy as blank for explicit configuration; domain consumption fails closed. An invalid persisted integer limit falls back to validated bounded configuration. Malformed persisted currency/type allow-lists fail closed rather than silently broadening the enabled set. Unknown persisted keys are not exposed or consumed.

No cross-request cache is introduced: database reads are authoritative and current workers see committed changes on their next read. Cache/Redis failure cannot remove limits. One section's values are fetched together. Critical commerce/refund/payout transactions acquire a shared PostgreSQL advisory transaction lock before domain locks; settings writers acquire its exclusive counterpart. A checkout therefore cannot mix old currency/cart/refund settings with a partially saved section.

## Timezone boundary

The pre-existing local mismatch remains: Laravel writes with UTC application configuration while the local PostgreSQL session uses Asia/Kolkata; naive TIMESTAMPTZ input can be interpreted accordingly. Phase 18 changes neither global/session database timezone nor any historical timestamp. Reports use persisted instants and explicit-offset PostgreSQL boundaries. Production should separately align write-time connection handling with UTC after an operational review; historical repair is outside this phase.

## Admin UI, routes and authorization

- GET `/admin/settings`, `admin.marketplace-settings.index`: auth + verified + `settings.view`.
- PUT `/admin/settings/{group}`, `admin.marketplace-settings.update`: auth + verified + `settings.manage`.

Routes use the existing web/CSRF middleware and private/no-store responses. The existing AppSidebar gains a permission-gated Marketplace Settings link. There is no hard admin-role bypass: a direct permission grant works, and a privileged role without a permission is denied. Manage-only access can mutate through the authorized endpoint; viewing the UI also requires settings.view.

`marketplace-settings/Index.vue` uses the existing AppLayout, Inertia forms, Wayfinder, Input/Label/Button and authorization helper. Nine section buttons select bounded per-section forms. List settings have checkboxes, integer fields use numeric inputs, decimals remain strings, boolean contact inclusion uses a checkbox, and optional contacts are normal email inputs. Help text, future-only warnings, processing/error/success states, read-only controls and the latest 30 audit events are displayed. No raw JSON, arbitrary key/type editor, HTML theme configuration or infrastructure-secret field is offered.

## Atomic updates, audit and events

`UpdateMarketplaceSettings` checks settings.manage, registry group/keys, explicit top-level `values`/`versions`, matching supplied keys and typed values before persistence. Client type/sensitive/group/rules/actor/version metadata are rejected. Actor identity derives from authenticated User. Unknown/secret-like keys are rejected without recording their values. Secrets remain environment/secret-manager configuration.

The entire section save, any new commission policy and every audit row commit atomically. Exclusive advisory lock protects creation of previously absent rows; row locks plus expected versions reject stale writers with “This section changed in another session. Reload before saving.” Unchanged values create no misleading audit event. `MarketplaceSettingChanged` is after-commit and carries group/key/actor ID/canonical old/new values/time only. Rollback dispatches nothing. There is no notification listener for this event.

Audit and updater FKs restrict account deletion, consistent with retained marketplace history. The existing account-deletion request provides a clear validation message instead of a database exception. Actor display names retain historical readability; events never cascade-delete.

## Performance and verification architecture

Only the small registered settings section is loaded; audit history is bounded to 30 rows. Group/key uniqueness indexes the read projection and the existing authoritative commercial indexes remain in place. No speculative commercial index, Redis dependency or second accounting ledger was introduced. Settings access adds bounded database work; production query tuning should follow measured traffic.

## Production considerations, known issues and deferred work

Deploy the forward migration before enabling settings UI. Existing compatibility values remain effective until overridden. Explicit production refund/payout policy remains required. Settings audit storage needs ordinary retention/backups; business-authorized future anonymization is separate. Commission scheduling remains the Phase 11 workspace's effective-dated contract; a settings save cannot silently replace a scheduled policy. Ordinary after-commit events are not an external delivery guarantee, and no settings-email infrastructure is introduced.

Known pre-existing issues: UserFactory::withTwoFactor() PHPStan missing return; optional fontaine build warning; local Laravel/PostgreSQL timezone mismatch; one intentional PostgreSQL Entitlement legacy-fixture skip. The workspace has no Git repository, so the file inventory records explicit changes rather than a Git diff.

Deferred: payment providers/secrets management, FX, tax, subscriptions, coupons, wallet, invoice rewrite, theme/HTML customization, preview-video uploads, remote settings/feature-flag platform, production deployment and historical timestamp repair. No Phase 19 work begins.
